# IIP 2.5.0 — audit, defect list, test and validation reports

Date: 2026-10-24. Starting point: release v2.4.0 (`Inventory-Intelligence-Dashboard_v2.4.0.zip`, the
archived Zenodo release). Every statement below is backed by a test, a command run in this session, or
a file reference; items that could not be verified are marked **not verified**.

## 1. Baseline (v2.4.0, before changes)

* Structure: FastAPI backend (18 routers, 21 tables), vanilla-JS frontend (17 pages, embedded template
  copy), EIDSF research engine, research-dataset validator, 141 automated tests.
* **Baseline test run:** `python -m pytest -q tests` -> **141 passed in 411 s** (Python 3.13.17).
* Confirmed working: authentication with hashed revocable sessions, organisation scoping of most queries,
  uploads with validation, EIDSF policy with certified bound, multi-item optimisation, Monte Carlo policy
  comparison, recommendation review audit trail, reproduction package (134 claims verified).

### Documentation vs code discrepancies found
* README/ARCHITECTURE claimed "real-time" monitoring and four segmentation dimensions as analytics; XYZ was
  not computed from data at all (see D1). `/api/health` advertised a capability list.
* README: "schema changes are applied automatically and add-only on start-up" - true, and also in production.
* `docs/RELEASE_READINESS_v2.2.md` (still the referenced readiness document) listed open items of 2.2.
* `docs/API.md` referred to version 2.4.0; `docs/schema.sql` described itself as "the production DDL" but
  was not kept in sync; `System_Description_Report.pdf` describes 2.0.
* The ERP page described live SAP/Oracle/Dynamics bridges with log lines that never happened (D3).

## 4. Inventory mathematics validation

All formulas in `docs/MATHEMATICAL_FORMULATION.md` §0 are checked against hand calculations
(`tests/test_inventory_math.py`): EOQ (PKR example 848.53; textbook 158.11; minimality and
ordering = holding at Q*), invalid inputs (negative, NaN, inf, missing, string, percentage-as-number),
z-values (0.95 -> 1.644854, 0.99 -> 2.326348, 0.5 -> 0), SS/ROP constant lead time (39.476 / 399.476),
random lead time (sigma_DLT 83.522, SS 137.382), boundaries (zero demand, zero lead time, CSL < 50 %),
unit conversion (weekly -> daily, factor sqrt 7 when mixed up), CSL vs fill rate (99.916 % vs 95 %),
ABC rule (70/20/6/4 -> A, A, B, C; dominant item A), XYZ thresholds and minimum history, forecast
metrics (MAE 1.75, RMSE, MAPE, WAPE 7 %, MASE), MAPE undefined with zeros, rolling origin without leakage.
The legacy wrappers used by the API are tested for the 2.5 fixes. Determinism: no randomness in these
functions; stochastic optimisation is seeded.

## 5. EIDSF / ABC research alignment

See `docs/RESEARCH_MAPPING.md` §A-D. Summary:
* decision vector (Q, SS) with defined domains, units and meaning - implemented in `eidsf/model.py`;
* objective ordering + holding (once) + shortage + purchasing (discounts) with controllable cost reported
  separately; constraints service, budget (order outlay; average-investment variant), warehouse pools, bounds;
* ABC phases, rank-based onlookers, scouts, feasibility-first comparison, repair, seeds, evaluation budget,
  convergence log verified by reading the code; no algorithm setting changed in 2.5;
* research engine byte-identical to 2.4.0 (`git diff v2.4.0 -- backend/eidsf` empty); 134 manuscript
  claims re-verified;
* open items requiring the thesis document or the researcher: purchasing term in the thesis objective,
  budget definition, dataset units, service-level type/targets, MOQ/pack-size integrality.

## 6. Security and multi-tenancy assessment

See `docs/SECURITY.md` §1 (checklist with evidence) and §2 (residual risks). Multi-tenancy: tenant scope
comes only from the session; helpers require `org_id`; the automatic matrix covers every API route for
anonymous access, foreign object ids, list/search/export leakage and cross-tenant writes; client-supplied
`org_id` is ignored; platform administrators are metadata-only. One cross-tenant data-mixing defect was
found and fixed (D8). Not done: external penetration test, PostgreSQL row-level security.
